# NexusOS Memory Vault

## Goal

A visitor opens the gallery card and, in under a minute, inspects a small company wiki the way NexusOS's inspection UI does. Done means: the page shows a real `nexusos` 0.1.0 status and document table, a typed search opens a note with its path and line range, wiki links jump between notes, and a context packet lists headings, siblings, and linked paths. Recorded tool output is labeled as NexusOS. A query that was not recorded is labeled as an in-browser fallback.

## In scope

- A sample vault, "Northline" (a freight-software company): a home page, concept and entity notes, a project note, two decisions, two ops SOPs, a workflow, a journal outage, and an inbox drill note. Notes use `[[wiki links]]`, including one unresolved target so link state is visible.
- `nexusos.toml` collection mappings so browse reports concepts, entities, projects, decisions, sops, workflows, journal, inbox, and wiki.
- At `bun run build`, a Python script creates a virtualenv, installs `nexusos==0.1.0` from PyPI, copies the vault to a temp workspace, runs `init --template blank --adopt` (so the starter `SCHEMA.md` is not mixed in), `index`, then records JSON from `status`, `search`, `browse`, `read`, `links`, and `context`. Absolute workspace paths are rewritten to `vault` so the file is portable. The script writes `src/data/capture.json`.
- Recorded searches (the chips): `vendor freeze`, `on-call`, `checkout outage`, `deploy window`, `acme payments`, `failover drill`. `read`, `links`, and `context` are recorded for every indexed document. `browse` is the full list.
- Browser UI in the visual language of the bundled inspection page (`src/nexusos/ui/index.html`): monospace, status line, counts, document table, bordered sections. Added on that page: a search box, a reader with line numbers, clickable wiki links taken from the recorded `links` resolution, and a context packet (headings with line numbers, sibling paths, linked paths, outgoing source lines).
- A query that matches a recorded term (trim, case-insensitive) shows that JSON and a "NexusOS 0.1.0" label. Any other non-empty query runs a small in-browser token match over the frozen `read` corpus and is labeled "Browser fallback". An empty box shows the document table, not a fake search.
- `demo.json` and this plan. One approved entry in `tracking/seen-bookmarks.json` for post `2085923509784756353`.

## Out of scope

- Running NexusOS, SQLite, or MCP in the browser or on GitHub Pages.
- Embeddings, vault editing, live indexing, or a server.
- Reimplementing FTS5 ranking. The fallback is a labeled token match, not a claim to be bm25.
- Changes to root config, CI, the gallery generator, `AGENTS.md`, `skills/`, or other apps.

## Stack

- Bun. `apps/nexusos-memory-vault/bunfig.toml` sets `minimumReleaseAge = 259200` under `[install]`, matching the repo root.
- Vite + React + TypeScript. `base: './'` so `bun run build` writes `apps/nexusos-memory-vault/dist` with relative asset URLs for `/tech-demos/nexusos-memory-vault/`.
- Plain CSS copied from the NexusOS inspection UI. No second component library; the page should look like that kernel view.
- Build-time only: Python 3.11+ (3.12 on this machine and on GitHub-hosted Ubuntu), `pip install nexusos==0.1.0`. `bun run build` runs `python3 scripts/record_vault.py`, then `tsc -b && vite build`. The client imports the generated JSON and never shells out.

## UX

- First screen is the kernel view: title "NexusOS Kernel Data", a one-line banner that the numbers come from a build-time `nexusos` 0.1.0 run, status (`ready` in green when the capture says so), counts, and the document table. The search box and six recorded chips sit above the table.
- Main interaction: type a query or press a chip. Hits show path, heading, `start_line–end_line`, the FTS snippet, and score. Choosing a hit opens that document and marks the recorded line range.
- Open document: recorded `read` text with line numbers. `[[links]]` that NexusOS resolved become buttons to the target path. An unresolved link stays text and says unresolved. Beside the reader: recorded outgoing and incoming links, then the context packet (headings with lines, siblings, linked paths).
- Empty query: the document table from `browse`, with no search label.
- A query that was recorded and returned zero hits stays an empty NexusOS result. It does not fall through to the browser matcher.
- If `capture.json` is missing a document the user opened, the pane says the recorded response could not be read.
- No API key.

## Risks

- GitHub Pages has no long-running Python process. Mitigation: record at build time and ship JSON. The client never imports `nexusos`.
- `bun run build` on Pages needs Python 3.11+ and PyPI. Ubuntu runners provide both. Mitigation: the script uses `python3 -m venv` and pins `nexusos==0.1.0`. `.venv` is gitignored.
- `browse` and `status` embed the absolute workspace path and a fresh `workspace_id` each init. Mitigation: rewrite absolute paths to `vault`. Timestamps and ids stay as that run emitted them. The UI does not depend on the id being stable across machines.
- A browser matcher could be mistaken for FTS5. Mitigation: a visible label on every result list, and recorded queries never take the fallback path, including a recorded empty list.
- Absolute asset paths would 404 under `/tech-demos/nexusos-memory-vault/`. Mitigation: Vite `base: './'`.
- Collection keys are path prefixes, and the longest match wins. A glob such as `ops/decisions/**` does not match. Mitigation: `nexusos.toml` uses prefixes (`ops/decisions`, `wiki/concepts`, …). The record script fails if `ops/decisions/adr-014-vendor-freeze.md` is not in collection `decisions`.
